## 1. 왜 1차 배경음악이 "웅웅"거렸나 — 원인 3가지

피드백이 정확했다. 수치로 확인된 원인:

| 문제 | 1차 버전 | 일반적인 게임 음악 |
|---|---|---|
| 스펙트럴 센트로이드 | **92 Hz** | 400~1200 Hz |
| 800Hz 이상 에너지 | **0.3%** | 10~25% |
| 300Hz 이하 에너지 | **82%** | 30~50% |

1. **에너지가 저역에 몰려 있었다** → 음정이 아니라 저역 덩어리로 들린다
2. **어택이 없었다** — 드론·패드(지속음)만 있어서 리듬도 선율도 안 잡힌다
3. **코드 진행이 모호했다** — 화음이 계속 깔려 있어 "진행"이 안 느껄진다

→ 근본 오류는 "어둡게 = 저역만"이라고 만든 것이다.
   실제로 어두운 게임 음악은 **저역이 두껍되 중·고역에 또렷한 음원이 있다.**

## 2. 샘플 4종 (16초 루프, 120BPM, Am–F–C–G ×2)

`tools/audio/gen_samples.py` — 파이썬 합성(외부 음원 없음 → 저작권 안전).
**전부 `public/` 밖**에 만들었다. 하나를 고른 뒤 본 스크립트로 옮긴다.

| 샘플 | 성격 | 센트로이드 | 800Hz+ | 폰 모사 | 용량 |
|---|---|---|---|---|---|
| **A** 던전 오스티나토 | 뜯는 저음 현 8분음표 + 킥 + 셰이커. **추진력** | 551Hz | 4.2% | -29.1dB | 146KB |
| **B** 첼로 + 심장박동 | 느리게 긋는 현. 1차와 성격은 같지만 **음정이 들린다** | 283Hz | 0.9% | -26.5dB | 112KB |
| **C** 부족 타악 | 드럼 주역 + 저음 금관 스탭. **액션·전투** | 1338Hz | 9.9% | -27.5dB | 179KB |
| **D** 성가풍 앰비언트 | 지속음이지만 코드 진행 + 고역 반짝임 | 481Hz | 6.0% | **-18.5dB** | 107KB |

> 1차 버전: 센트로이드 **92Hz** / 800Hz+ **0.3%** — 네 개 모두 3~14배 개선됐다.

### 음원 설계
어택이 있는 음원을 새로 만들었다:
- `pluck()` — 배음 가산합성. **높은 배음이 먼저 사라져** 실제 현처럼 들린다
- `bowed()` — 톱니 + 비브라토. 지속되지만 배음이 있어 음정이 잡힌다
- `bell()` — 비배음 부분음. **고역 담당** — 이게 있어야 폰에서 음악으로 들린다
- `kick()` `tom()` `shaker()` `stab()` — 리듬과 마디 강조

### 뱀서류에 맞는 선택 기준
한 판이 길고 곡이 **수십 번 반복**된다. 그래서:
- 선율이 뚜렷하면 금방 질린다 → A/C 처럼 **패턴 위주**가 유리
- 반대로 너무 없으면 1차 버전처럼 "웅웅"이 된다 → B/D 는 그 경계
- **개인적으로는 A**를 권한다. 추진력이 있고(반복 플레이와 맞음) 선율이 없어 덜 질린다.
  전투감을 더 원하면 C.

## 3. ⚠️ 루프 이음 — OGG 패딩 문제 (선택 후 확인 필요)

4개 모두 파형 상으로는 **연속**이다(이음부 점프가 직전·직후 기울기와 같은 수준).
다만 실측 길이가 **16.01초**로 나온다 — Vorbis 인코더가 앞뒤에 패딩을 넣기 때문이다.

Phaser 의 `loop: true` 는 디코드된 버퍼 전체를 돌리므로 **패딩만큼(약 10ms)
빈틈이 생길 수 있다.** 실제로 들리는지는 귀로 확인해야 한다.

들린다면 해결책(비용 순):
1. 루프 지점을 코드로 지정 — `sound.play({ loop: true })` 대신 Web Audio
   `loopStart/loopEnd` 를 직접 설정
2. 곡을 2번 이어붙여 내보내고 끊김 지점이 곡 중간에 오게 (임시 회피)
3. `.wav` 로 배포 (패딩 없음, 대신 용량 10배)

## 4. 골드 시스템

### 드랍
| 대상 | 양 |
|---|---|
| 일반몹 | 확률 12%, 1~2개 |
| 엘리트 | **확정 10개** |
| 보스 | **확정 25개** |

- 동전은 **눈에 보이는 개체**로 떨어진다. 숫자만 오르면 보상감이 없다
- 튀어나오는 초기 속도 + 마찰 → 여러 개가 한 점에서 나와도 흩어져 보인다
- 회전 연출: 가로 폭을 진동시킨다(`Math.cos(spin)`) — 스프라이트 없이 동전처럼 보이는 가장 싼 방법
- 반사광 하이라이트가 있어야 금속으로 읽힌다

### 획득
- `player.pickupRadius`(기본 50) 안에 들어오면 빨려온다
  → **죽어 있던 config 항목을 되살렸다.** 젬이 즉시 지급되는 구조로 바뀐 뒤
    이 값은 아무 효과가 없었다(튜너 라벨도 '젬 획득 범위' → '골드 획득 범위'로 수정)
- **한 번 자석에 걸리면 범위를 벗어나도 계속 따라온다** — 안 그러면 경계에서
  붙었다 떨어졌다 하며 어색하다
- 14초 뒤 사라진다(화면 누적 방지). 마지막 1.5초는 깜빡여서 예고한다

### 표시
- **HUD 좌상단** 레벨 아래: 동전 아이콘 + 숫자
- **결과 화면**: `+획득 골드` + `보유(누적)` — 금색 강조 박스

### 영구 저장
- `localStorage` 키 `wg_gold_v1` 에 누적
- **`endGame()` 에서 딱 한 번 적립**한다. `buildResult()` 는 여러 번 호출될 수
  있으므로 거기서 하면 중복된다(정적 점검으로 `addGold` 호출이 1회임을 확인)
- ⚠️ 탭을 닫으면 그 판 골드는 사라진다(사망 시점에만 적립). 의도한 동작 —
  끝까지 하게 만든다

### 왜 골드는 킬 수 비례여도 괜찮은가
룬은 슬롯이 3칸뿐이라 개수가 폭주하면 UI가 무너졌다(실제로 100개+ 사태가 있었다).
골드는 **그냥 숫자**라 많아도 문제가 없다.
단 **업그레이드 가격은 후반 킬 수를 기준으로** 정해야 한다 —
10분 플레이 시 킬이 수천이므로 12% 드랍이면 판당 수백 골드가 모인다.

## 5. 다음 단계 — 골드 상점 (아직 구현 안 함)

사용자 계획: 게임 종료 시 골드로 **시작 스탯** 강화.

설계 시 정해야 할 것:
- 어디서 사나 — **결과 화면에 상점 탭**을 붙이는 게 가장 자연스럽다(이미 죽어서 멈춘 상태)
- 무엇을 파나 — 공격력 / 최대 체력 / 회복 / 이동속도. 각 5단계 정도

- ⚠️ **상한 필수.** 영구 강화가 무한이면 초반 난이도가 무의미해지고,
  신규 유저와 기존 유저의 경험이 완전히 달라진다
- 저장 키는 `wg_upgrades_v1` 로 분리 (골드와 별도 — 초기화 정책이 다를 수 있다)

## 7. ✅ 배경음악 확정 — 샘플 A "던전 오스티나토"

`tools/audio/gen_bgm.py` 를 A 구성으로 교체(1차 드론 버전은 폐기).
`public/audio/bgm_dungeon.ogg` **295KB** (+ m4a 폴백).

### 16초 → 32초로 확장 + 구성 변화
16초면 한 판(2~10분)에 8~40회 반복된다. 32초(16마디)로 늘리고
**4마디 단위로 구성을 바꿔** 반복 체감을 낮췄다:

```
1~4마디   intro    뼈대만 (오스티나토 + 킥)
5~8마디   develop  아르페지오 + 톰 추가
9~12마디  breathe  드럼을 덜어내고 종 → 숨 돌림 ← 이 대비가 핵심
13~16마디 full     전부 + 마지막 마디 톰 필로 1마디로 되돌아감
```

### 음색 튜닝 2회 (둘 다 과했다가 되돌림)
| | 센트로이드 | 800Hz+ | 폰 모사 | 판단 |
|---|---|---|---|---|
| 1차 드론 버전 | 92Hz | 0.3% | -27.7dB | ❌ "웅웅" |
| 확장 직후 | 571Hz | 3.5% | -31.3dB | 폰에서 약함 |
| 고역 셸프 1.6배 | **1770Hz** | 13.8% | -28.9dB | ❌ 쉬쉬거려 어두운 톤이 깨짐 |
| **최종** | **458Hz** | **4.5%** | **-30.1dB** | ✅ 승인된 샘플 A(551Hz/4.2%)와 같은 profile |

셰이커 대역을 3k~21kHz → **2k~11kHz** 로 낮춘 게 결정적이었다.
3kHz 이상 노이즈는 '쉬쉬'거려서 던전 톤을 깬다.

### 🔧 루프 빈틈 제거 (실측으로 확인된 필요 조치)
인코더 패딩을 정확히 측정했다:

```
악보 길이   1,411,200 샘플 = 32.000000 s
OGG 디코드  1,411,648 샘플 = 32.010159 s  → 패딩 +448 샘플 (+10.2 ms)
M4A 디코드  1,412,096 샘플 = 32.020317 s  → 패딩 +896 샘플 (+20.3 ms)
```

컨테이너 메타데이터는 32.000s 라고 보고하지만 **실제 디코드 결과에는 패딩이 붙는다.**
Phaser 의 `loop` 는 버퍼 전체를 돌리므로 매 바퀴 10ms 무음이 끼어든다 —
120BPM 리듬 트랙에서는 **박자가 튀는 것으로 들린다.**

→ `playBgm()` 에서 Web Audio 소스에 루프 지점을 직접 지정:
```js
src.loopStart = 0
src.loopEnd = BGM_LOOP_SEC   // 32.0
```

> ⚠️ **`main.js` 의 `BGM_LOOP_SEC` 와 `gen_bgm.py` 의 `LOOP` 는 반드시 같아야 한다.**
> BPM·마디 수를 바꾸면 둘을 같이 고쳐야 한다. (정적 점검에 넣어뒀다 —
> `gen_bgm.py` 의 `BPM × BARS` 로 계산한 값과 `main.js` 상수를 대조한다)

볼륨은 `BGM_VOLUME = 0.55` 로 상수화했다.

## 8. 판당 골드 추정 — 상점 가격 기준

시뮬 200판 기준(생존 중앙 85초, 킬 평균 136, 엘리트 2.04):

```
판당 예상 골드 ≈ 61
```

상점 가격을 정할 때의 기준선이다. 1단계 업그레이드를 **50~80** 정도로 두면
"한 판 하면 하나 산다"는 리듬이 되고, 5단계까지 지수 곡선으로 올리면
장기 목표가 생긴다.

> ⚠️ 이 추정은 **현재 밸런스(생존 85초)** 기준이다. 초반 급사 문제를 고쳐
> 생존이 길어지면 골드도 같이 늘어나므로 상점 가격은 **그 뒤에** 확정해야 한다.
